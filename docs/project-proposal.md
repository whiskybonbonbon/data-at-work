# Data at Work — Project Proposal

> Even a single piece of data is supported by countless jobs.

## 1. Project Overview

Data at Work is an anthropomorphic story set inside computers and web services. Its protagonist is a piece of data, and its characters reveal how the technologies supporting digital services work together.

| Item | Description |
|---|---|
| Working title | Data at Work |
| Genres | Technology education, workplace story, adventure, comedy |
| Concept | Engineering × anthropomorphism × education × entertainment |
| Protagonist | A newly created piece of data |
| Setting | The internal world of computers and web services |
| Audience | Everyone from programming beginners to working engineers |
| Possible formats | Manga, animation, and web content |
| Main themes | How technology works, division of responsibilities, cooperation, and growth |

Rather than presenting technical knowledge as a lecture, the project turns technologies into characters so readers can learn naturally through an entertaining story. Beginners should discover how computers work, while experienced engineers should find recognizable technical details and humor.

## 2. Setting

The story takes place in Digital World (working name), a vast information city. Whenever a user presses a button, sends a message, or plays a video, countless specialists work behind the scenes.

| District | Primary responsibility | Example technologies |
|---|---|---|
| Frontend District | Display and user interaction | HTML, CSS, JavaScript, React |
| Backend District | Request processing and data transformation | APIs, Node.js, Python, Java |
| Database District | Information storage and management | SQL, DBMSs, Redis |
| Network District | Communication and transmission | TCP, UDP, IP, DNS, routers |
| Central Processing District | Instruction execution | CPUs, threads, processes |
| GPU Computing District | Massively parallel computation | GPUs, shaders |
| Infrastructure District | Stable system operation | Operating systems, Linux, Docker, monitoring |
| Security District | Information protection | Authentication, encryption, firewalls |

The districts are not independent countries. Like real systems, they constantly cooperate. Their geography is a teaching metaphor and should not oversimplify the relationships or boundaries between technologies.

## 3. Protagonist

### Data-chan (working name)

- **Role**: A traveler exploring the information city
- **Personality**: Curious and slightly clumsy
- **Goal**: Discover why she was created and what role she is meant to fulfill
- **Defining trait**: She meets different technologies while being processed, transformed, stored, and transmitted

One day, a user action creates a new piece of data. The protagonist does not yet know her purpose.

> “Why was I created? What am I supposed to do?”

She travels from the frontend to the backend, databases, and networks. By meeting characters with different jobs, she learns how information systems support society.

The story follows her as one continuous protagonist, but real data may be copied, transformed, or regenerated. Technical explanations must explicitly distinguish those operations from the story's fictional continuity.

## 4. Character Design Direction

Characters and their technical roles are maintained in the [character list](../characters/character-list.md).

- Bits are tiny inhabitants represented by zeros and ones who make up the protagonist.
- Packets are transport capsules that carry data through the network.
- Threads are workers representing flows of instruction execution.
- The CPU is the central processing department that executes the threads' instructions.
- TCP and UDP are delivery managers with contrasting approaches to reliability and overhead.
- Programming languages represent technical traditions or organizations rather than the entities that execute instructions.

## 5. Basic Story Structure

Each episode begins with a user action or an event inside the system. An episode about sending a message could follow this conceptual sequence:

1. A user sends a message.
2. The protagonist data is created.
3. The frontend receives the input.
4. The data is placed into communication units and travels through the network.
5. The backend receives the request and processes the data.
6. The data is stored in a database when necessary.
7. The result returns to the user and appears on the screen.

This is a conceptual data flow for a web application. The actual communication and storage processes vary with system architecture, and the work should say so when appropriate.

## 8. Creative Rules

1. **Preserve essential technical roles:** Data is processed, threads represent flows of execution, and CPUs are hardware that executes instructions.
2. **Separate metaphor from fact:** “Riding in a packet” is a fictional metaphor for data being placed into a communication unit.
3. **Use one main theme per episode:** Avoid overloading the story with explanations. Teach one central concept through an incident or problem.
4. **Serve both beginners and experienced readers:** Keep the main story easy to follow while including deeper details for engineers.
5. **Maintain the protagonist's identity:** Establish story rules that let readers follow the protagonist through copying, transformation, and deletion.

## 10. The Project's Core Appeal

The project's central appeal is that it makes normally invisible computer systems understandable through characters' jobs and relationships. It goes beyond turning IT terms into mascots: the protagonist's journey shows how frontends, backends, networks, databases, CPUs, GPUs, and other technologies cooperate.

> Behind every service we use without a second thought, countless technologies are working today.

The project aims to inspire interest in technology and affection for its characters at the same time.
